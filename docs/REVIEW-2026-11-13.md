# NAFS: проверка входа и обновление интерфейса — 13.11.2026

Работа выполнена поверх `nafs-update`, исходный commit `32a250548c020f476bfc646700b999c5bf8c56bd`. Локальная ветка: `fix/telegram-auth-cinematic-audit`. Production Railway, внешняя Supabase и секреты не изменялись.

## Что исправлено

- Воспроизведён дефект `guard`: ошибка RPC раньше давала тот же ответ, что действительное превышение лимита. Теперь только булево `false` от `consume_rate_limit` даёт HTTP 429 с `Retry-After`. Отсутствующая миграция, запрет доступа, сбой сети, неверная конфигурация и некорректный ответ имеют отдельные коды 503. Подмена Origin — 403; подпись/срок Telegram — 401. Неожиданные исключения не возвращают текст провайдера.
- Логи содержат только случайный диагностический ID, код, статус, имя операции и безопасный SQL-код. Нет initData, cookie, Telegram ID, имени пользователя, ключей или содержимого рабочего пространства.
- Установленный Supabase SDK проверен с `sb_publishable_` и `sb_secret_` через подменённый HTTP-транспорт. Публичный ключ не допускается на месте серверного и наоборот. **Это не проверка настоящих ключей Railway.**
- Telegram: официальный SDK, HMAC, auth_date, защита повторного использования, случайные HttpOnly/Secure/Partitioned cookie; запись сессии, расход подписи и успешный вход объединены в транзакцию. Ошибка записи откатывает расход подписи. Одновременные вызовы входа на клиенте объединяются. Повторное открытие с действующей сессией не создаёт лишних аккаунтов или успешных входов.
- При недоступном Telegram-входе показывается экран восстановления, а не молча редактируемая гостевая копия. Явный выход/удаление сохраняют гостевой выбор только для текущего запуска; следующий запуск или другой Telegram-аккаунт не наследуют эту отметку. В sessionStorage хранится только хеш запуска.
- Владелец определяется по серверной Telegram-сессии и записи `telegram_identities`, ID `6123609704`. Email-аккаунт с похожим ID прав не получает. Статистика владельца включает поиск, страницы по 20 пользователей, регистрацию и активность за 24 часа/7/30 дней, первый успешный вход, последний визит и число входов. Личные задачи и дневники не запрашиваются.
- Миграция 006 повторяемая. Новая 007 добавляет атомарный вход и агрегаты статистики без удаления данных. RLS и ограничения прав сохранены. `first_login_at` для старых неизвестных входов остаётся пустым; прежние счётчики сохраняются, их историческую точность восстановить из отсутствующих журналов невозможно.
- Обычный режим: лес, горы, графит, зелёный и золото. Исламский: дворик, камень, тёплый свет и отдельные поверхности карточек. Пять вкладок, светлая тема, RTL, safe areas, reduced motion. «Сегодня» стало компактнее, мотивация видна раньше. Каталог и статистика уплотнены; подробный недельный отчёт раскрывается по нажатию. Убраны рекламные надписи о бесплатности.
- Два набора по 400 отдельных сообщений, каждое с RU/EN/TR/AR. Старый комбинаторный генератор удалён. Авторские исходники в `content/motivation-authored`; сборщик только объединяет и валидирует готовые строки. Дневной цикл 400 локальных дат, отдельный выбор по режиму, ручное обновление и избранное. Старые сохранённые сообщения доступны по прежним ID.
- Перенос гостевых определений задач/привычек и избранного требует подтверждения. Облачная история не перезаписывается, история гостя остаётся локально. Полное объединение историй и связывание email/Telegram аккаунтов не реализованы.

## Проверки

В текущей сессии выполнены `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Точные итоговые числа и браузерные результаты — в `VERIFICATION.md`.

Регрессии включают: реальный Supabase SDK с подменённым транспортом, действительную тестовую HMAC-подпись, подделку и replay, недоступную БД, изоляцию владельца, неизменность старого состояния, транзакционные SQL-проверки PostgreSQL/PGlite, повторный запуск 006/007, RLS/права, каскадное удаление, задачи/привычки/марафоны/XP/таймеры, обе библиотеки и сохранение избранного.

Браузер: Chromium с мобильными размерами, светлая/тёмная тема, RU/EN/TR/AR, все вкладки, ограниченная высота для имитации клавиатуры. Это не физический Safari или настоящий Telegram WebView. Независимый переводческий/религиозный редактор не участвовал: перед публичным выпуском нужна такая проверка. Автотесты не могут доказать уникальность смысла или идеальное качество перевода.

## Что требуется перед staging

1. Дать подключению GitHub доступ на запись в Contents и Pull requests для `Nafs-`: и плагин, и авторизованный CLI получили 403 при создании ветки. Токены в чат не отправлять. Локальные изменения/ветка сохранены; до успешной записи ссылка на PR отсутствует.
2. Создать отдельный Railway staging и отдельный тестовый Supabase. Не направлять тестовый деплой на production DB. Для существующей тестовой базы с 001–006 применить `007_auth_reliability.sql`; для новой — 001–007 по порядку.
3. В staging: `APP_URL=https://<staging-host>` (точный origin, без пути), URL Supabase, публичный ключ, server-only secret/service-role key и токен **тестового** бота. Если используется сборка с NEXT_PUBLIC_ переменными, задать их до build. Не копировать реальные пользовательские данные в preview.
4. BotFather: `/newbot` для тестового бота; `/mybots` → Bot Settings → Configure Mini App или Menu Button → HTTPS staging URL. Установить имя NAFS и иконку. Точный вид меню BotFather может меняться.
5. Проверить HTTPS и сертификат, что WebView открывает именно заданный origin, прокси передаёт корректный `X-Forwarded-For`. IP участвует только в ограничении частоты и не даёт прав. Не подменять Origin доверенным значением на сервере.

## Настоящий end-to-end сценарий

- Открыть staging через меню **тестового** бота. Не пересылать initData и cookie в чат, GitHub или скриншоты.
- Убедиться, что профиль показывает Telegram-аккаунт. Создать задачу, привычку, марафон; завершить день, сохранить избранное. Закрыть/открыть Mini App и обновить: состояние восстановилось, login_count не растёт от каждой перерисовки.
- Войти двумя Telegram-аккаунтами на одном устройстве. У второго нет данных первого. Старый открытый экран не должен сохранять изменения в новый аккаунт: 409 WORKSPACE_CHANGED.
- От владельца открыть `/admin`, проверить поиск/страницы/статистику. От обычного пользователя и гостя панель не раскрывает данные, API отказывает.
- Прервать связь с тестовой БД: экран восстановления, отдельный код и диагностический ID. В серверном логе найти этот ID. **Причина прежнего production-сбоя остаётся неподтверждённой без такого журнала или реального E2E.**
- Проверить закрытие/открытие, выход, новую сессию, просроченный запуск и отмену сети во время входа. Не обходить replay: если cookie не сохранилась, открыть Mini App заново для свежего запуска.
- Проверить экспорт и удаление на одноразовом тестовом аккаунте; убедиться, что сессии, профиль, согласие на сообщения и личные записи удалены.
- Рассылку проверять только на явно согласившихся тестовых получателях после проверки текста и аудитории. Сообщения реальным пользователям в ходе этой работы не отправлялись.

Production обновлять только после отдельного разрешения владельца и проверки staging. Локальный успешный build не доказывает работоспособность конкретной Railway/Supabase-конфигурации.
